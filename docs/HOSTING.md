# Свой сайт для «Каретки»

Чтобы открыть редактор под своим именем, достаточно подключить домен к действующему проекту Netlify. Чтобы хранить аккаунты, заказы и рукописи на выбранном вами сервере, разверните приложение на VPS. Ниже описаны оба пути. Продажи можно включить после запуска сайта и проверки магазина ЮKassa.

## 1. Домен на действующем проекте Netlify

1. Зарегистрируйте домен на свой аккаунт у регистратора. Для примеров в инструкции используется `write.example.org`. Замените его своим именем.
2. Откройте **Netlify → проект karetka → Domain management → Production domains** и добавьте своё имя как custom domain.
3. Для поддомена `write` создайте у регистратора запись `CNAME` на имя проекта, которое покажет Netlify. Для корневого домена используйте значения и тип записей из панели этого проекта. Удаляйте конфликтующую запись только для переносимого имени. Почтовые записи домена сохраняйте.
4. Дождитесь подтверждения DNS и выпуска TLS-сертификата в Netlify. Откройте `https://ваш-домен/api/health`. Когда ответ успешен, назначьте домен основным. Если подключаете оплату, укажите окончательный origin и замените адрес вебхука в ЮKassa.
5. GitHub остаётся источником приложения. Для действующего проекта используются ветка `main`, команда `npm test`, каталог публикации `dist` и функции `netlify/functions`. Изменение в `main` запускает следующую публикацию. Параметры магазина задавайте в Project configuration → Environment variables, в контексте Production, со scope Functions. После изменения переменных повторите деплой.

На том же Netlify-проекте у аккаунтов и облака остаётся тот же серверный набор данных. Локальные книги, вход и офлайн-кэш браузер ведёт по отдельности для каждого домена. Перед переключением см. раздел 8. [Настройка DNS в Netlify](https://docs.netlify.com/manage/domains/configure-domains/configure-external-dns/)

### Как войти владельцу действующего Netlify-проекта

Откройте в приложении **Кабинет**. В панели именно вашего проекта Netlify перейдите в **Data & Storage → Blobs → karetka-commerce-v1 → operator/owner-setup**. После первого открытия кабинета сайт создаёт там приватную запись. Скопируйте её поле `activationCode`. В приложении раскройте **Для владельца сайта** и выберите **Первый вход владельца**, проверьте указанный логин `alchemist308`, введите код активации и придумайте пароль. После активации сервер заменяет поле с кодом отметкой времени. Сохраните выданный **резервный код аккаунта** в менеджере паролей. Он нужен для восстановления доступа.

Обычная регистрация не выдаёт роль владельца. Владельцу доступны платные функции без оплаты, управление доступом пользователей и сведения для обработки заказов. Вход в админку проходит через тот же кабинет. Вариант с собственным значением `KARETKA_OWNER_SETUP_HASH` использует код оператора, описанный ниже.

## 2. Отдельный VPS и DNS

Подойдёт VPS с Ubuntu 24.04 LTS, публичным IPv4 и SSH. Для первого запуска ориентир — 2 vCPU, 2 ГБ RAM и 25–40 ГБ SSD. Память понадобится и для сборки, и для одновременных входов с проверкой паролей. Планируйте дополнительное место для двух копий рабочей базы на время восстановления. Размер диска и нагрузку проверяйте по фактическому объёму рукописей. Для российского запуска, где сервис собирает персональные данные граждан РФ, выберите VPS и базу в российском дата-центре. При выборе провайдера уточните также регион резервных копий. В базе хранятся сведения об аккаунтах и заказах, в том числе адрес для чека. Общие требования к месту сбора и предусмотренные законом исключения изложены в ч. 5 ст. 18 закона № 152-ФЗ. [Изменения правил локализации](https://www.consultant.ru/document/cons_doc_LAW_507825/9a83d89e3db49659e94af1deec8c774cd88ab29b/)

У регистратора создайте `A`-запись `write` на IPv4 VPS. Запись `AAAA` добавляйте при настроенном IPv6 и доступности сервера по нему. На сетевом экране провайдера разрешите входящие TCP 80 и 443, SSH — со своих административных адресов. UDP 443 можно открыть для HTTP/3. Порт Node 8080 доступен только внутри сети Compose. Проверьте, какие адреса DNS возвращает на другом компьютере.

```sh
dig +short write.example.org A
dig +short write.example.org AAAA
```

Сервер запускает два контейнера. Caddy принимает HTTPS, получает и продлевает сертификат. Node обслуживает редактор и API. SQLite хранит аккаунты, заказы, зашифрованное содержимое и метаданные в постоянном томе `karetka_data`. Сертификаты Caddy хранятся отдельно. [Как Caddy выпускает сертификаты](https://caddyserver.com/docs/automatic-https)

## 3. Установка Docker и приложения

Подключитесь по SSH. Команды идут от пользователя с `sudo`. После `sudo -i` следующие блоки выполняются в административной оболочке. На свежей Ubuntu установите пакеты и клонируйте проект.

```sh
sudo -i
apt-get update
apt-get install -y ca-certificates curl git openssl dnsutils
install -d -m 0755 /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
chmod 0644 /etc/apt/keyrings/docker.asc
. /etc/os-release
cat > /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $VERSION_CODENAME
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
apt-get update
apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
systemctl enable --now docker
docker compose version
git clone https://github.com/alchemist308/karetka.git /opt/karetka
cd /opt/karetka
umask 077
cp .env.example .env
chmod 600 .env
```

Если Docker уже установлен из официального репозитория, достаточно проверить `docker compose version` и перейти к клонированию. [Установка Docker на Ubuntu](https://docs.docker.com/engine/install/ubuntu/)

Откройте `/opt/karetka/.env` текстовым редактором. Установите `PUBLIC_ORIGIN=https://write.ваш-домен`, `KARETKA_OWNER_LOGIN=alchemist308`, `BILLING_MODE=off`. Укажите свой полный HTTPS-адрес без пути. Хостинг, регистрация и бесплатная работа могут запуститься до подключения магазина.

Сгенерируйте код только для этой установки. Первая команда ниже рассчитана на новый сервер. Она откажется перезаписать существующий файл. В конфигурацию попадёт SHA-256 кода.

```sh
cd /opt/karetka
( umask 077; set -C; openssl rand -hex 32 > /root/karetka-owner-activation.txt ) &&
  owner_hash=$(tr -d '\n' < /root/karetka-owner-activation.txt | sha256sum | cut -d ' ' -f1) &&
  sed -i "s/^KARETKA_OWNER_SETUP_HASH=.*/KARETKA_OWNER_SETUP_HASH=$owner_hash/" .env
release=$(git rev-parse --short=12 HEAD)
sed -i "s/^KARETKA_RELEASE=.*/KARETKA_RELEASE=$release/" .env
docker compose config --quiet
docker compose build --pull app
docker compose up -d --wait
docker compose ps
```

В приватном SSH-терминале прочитайте `/root/karetka-owner-activation.txt`. Откройте **Кабинет → Для владельца сайта → Первый вход владельца** на своём сайте, введите этот код, назначьте пароль и сохраните отдельный резервный код. Повторное применение активационного кода не создаёт второго владельца. Секрет магазина, код активации и резервные коды храните вне Git.

Откройте сайт на телефоне, а с компьютера выполните следующие проверки.

```sh
curl -fsS https://write.example.org/api/health
curl -fsS https://write.example.org/api/account/session
curl -fsSI https://write.example.org/sw.js
docker compose logs --tail=100 web app
```

`/api/health` должен вернуть HTTP 200, а `/api/account/session` без cookie — пользователя `null` и список тарифов. Создайте тестовый аккаунт автора, включите зашифрованное облако в кабинете, напишите несколько строк, дождитесь сохранения в сети, войдите тем же логином на другом устройстве и включите облако там. После первого открытия отключите сеть, напишите ещё строку, верните сеть и проверьте появление правки на втором устройстве. Перед приглашением авторов пройдите также восстановление тестового аккаунта по резервному коду.

## 4. Тарифы и настройка продаж

Покупатель может выбрать «Кошелёк ЮMoney» или другие способы, доступные на странице ЮKassa. Для приёма денег продавцу нужен подключённый магазин ЮKassa со своим идентификатором и секретным ключом. В кабинете магазина проверьте доступность способа ЮMoney. Переход покупателя обратно в «Каретку» открывает историю заказа. Для выдачи тарифа сервер сверяет результат с API провайдера. [Оплата кошельком ЮMoney](https://yookassa.ru/developers/payment-acceptance/integration-scenarios/manual-integration/yoo-money) · [Как получить параметры магазина](https://yookassa.ru/developers/payment-acceptance/getting-started/quick-start)

| Тариф | Рукописей в личном облаке | Контрольных версий на рукопись | 30 дней | 365 дней |
| --- | ---: | ---: | ---: | ---: |
| Черновик | 1 | 0 | 0 ₽ | 0 ₽ |
| Автор | 20 | 5 | 299 ₽ | 2 990 ₽ |
| Мастерская | 100 | 25 | 599 ₽ | 5 990 ₽ |
| Владелец | Без тарифной квоты | Без тарифной квоты | 0 ₽ | 0 ₽ |

Локальный редактор доступен гостю. Автор с бесплатной учётной записью может один раз включить пробный «Автор» на 14 дней без карты. Подписки оплачиваются на фиксированный срок. Для следующего периода автор подтверждает отдельную покупку. Оплаченный заказ учитывается после проверки сервером ЮKassa. Тарифы и цены определены в `server/billing.mjs`, права проверяются на сервере. Смена цены применяется к новым заказам. После истечения доступа автор может прочитать и экспортировать ранее сохранённые книги.

| Переменная | Что указать |
| --- | --- |
| `BILLING_MODE` | `off` для запуска, `test` для тестового магазина, `live` для реального |
| `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY` | Идентификатор и закрытый ключ соответствующего магазина |
| `RECEIPT_MODE` | `manual_npd` — продавец на НПД вручную регистрирует доход и передаёт чек. `provider` — данные чека передаются подключённому решению ЮKassa |
| `RECEIPT_VAT_CODE` | Для `provider` укажите согласованный со своим бухгалтером и ЮKassa код ставки НДС |
| `SELLER_NAME`, `SUPPORT_EMAIL` | Настоящие реквизиты продавца и работающий адрес поддержки |
| `OFFER_URL`, `PRIVACY_URL` | Публичные HTTPS-ссылки на вашу оферту и политику обработки данных |

1. Зарегистрируйте тестовый магазин в ЮKassa. Для проверки удобен отдельный VPS или стенд с собственными именем и томом. При `BILLING_MODE=test` используйте тестовые учётные данные магазина. После записи переменных выполните `docker compose up -d --force-recreate app`.
2. В личном кабинете магазина добавьте адрес входящих уведомлений `https://ваш-домен/api/pay/webhook` и события `payment.succeeded`, `payment.canceled`, `refund.succeeded`. Адрес должен быть доступен извне по HTTPS. Проверьте успешную покупку по тестовым данным ЮKassa, отмену и возврат. В кабинете проверяйте статус конкретного заказа. Тестовая оплата служит для проверки расчётов и не открывает покупателю боевой доступ.
3. Оформите подключение реального магазина на своего продавца, согласуйте схему чеков и подготовьте реквизиты, оферту с ценой/периодом/порядком отказа и возврата, политику обработки данных. Разместите документы по ссылкам, которые вводите в `.env`. Эти документы должны соответствовать выбранной форме деятельности и фактической обработке информации.
4. На **рабочем** сервере установите реквизиты реального магазина, его webhook и `BILLING_MODE=live`. Перезапустите приложение с обновлённой конфигурацией. Проверьте статус кабинета и доступность ссылок перед открытием продаж. Код приложения не выставляет платежи пользователям при первой авторизации.
5. При `manual_npd` зарегистрируйте полученный доход в «Мой налог» и передайте чек покупателю. Для `provider` убедитесь в успешной фискализации чека у своего оператора. Возврат денег оформляйте в личном кабинете ЮKassa. После уведомления сверяйте изменения в заказе.

[Тестовый магазин и карты](https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing) · [Входящие уведомления](https://yookassa.ru/developers/using-api/webhooks) · [Чеки для компаний, ИП и НПД](https://yookassa.ru/developers/payment-acceptance/receipts/basics)

## 5. Резервная копия

Код на GitHub восстанавливает приложение. База нужна отдельно для аккаунтов, покупок, прав и облачных рукописей. Запущенное приложение пишет в SQLite WAL. Для согласованной копии используйте встроенную команду `backup`. Она создаёт единый снимок, проверяет его и сохраняет ETag записей, необходимые для синхронизации устройств. [Снимки SQLite через VACUUM INTO](https://www.sqlite.org/lang_vacuum.html)

```sh
cd /opt/karetka
umask 077
install -m 0700 -d /var/backups/karetka
backup="/var/backups/karetka/$(date -u +%Y%m%dT%H%M%SZ).sqlite"
docker compose exec -T app node server/sqlite-store.mjs backup - > "$backup.partial" &&
  docker compose exec -T app node server/sqlite-store.mjs verify - < "$backup.partial" &&
  mv "$backup.partial" "$backup" &&
  sha256sum "$backup" > "$backup.sha256"
```

Эти команды можно сохранить в root-скрипт и запускать через cron ежедневно, например в 03:15 по времени VPS. Делайте ещё одну копию перед обновлением. Передавайте архив и контрольную сумму в зашифрованное хранилище вне VPS. Сохраняйте зашифрованную копию `.env` отдельно. Снимок базы содержит хеши сессий, учётные записи, историю платежей и зашифрованные рукописи. Доступ к архивам предоставляйте только операторам. Проверьте свободное место командой `df -h` и доставку последней копии во внешнее хранилище. Задайте срок хранения с учётом своих требований.

## 6. Как восстановить данные

Восстановление пишет в **новый том**. Исходный том остаётся доступным для возврата. В рабочей системе сначала предупредите авторов и остановите публичный сервер на время переключения. Приложение, уже открытое офлайн, может продолжать локальное сохранение.

```sh
cd /opt/karetka
backup=/var/backups/karetka/ИМЯ_ВЫБРАННОЙ_КОПИИ.sqlite
sha256sum -c "$backup.sha256"
docker compose exec -T app node server/sqlite-store.mjs verify - < "$backup"
restore_volume="karetka_restore_$(date -u +%Y%m%dT%H%M%SZ)"
KARETKA_DATA_VOLUME="$restore_volume" docker compose run --rm -T --no-deps app \
  node server/sqlite-store.mjs restore - < "$backup"
```

Оболочка должна завершить каждую проверку с кодом 0. На новом сервере, где приложение ещё не запущено, вместо `docker compose exec -T app` используйте `docker compose run --rm -T --no-deps app` для проверки. Для планового восстановления на работающем сервисе заранее поставьте запись на паузу и учтите изменения и платежи, появившиеся после даты копии.

```sh
docker compose stop web app
cp -p .env /root/karetka-before-restore.env
sed -i "s/^KARETKA_DATA_VOLUME=.*/KARETKA_DATA_VOLUME=$restore_volume/" .env
docker compose up -d --wait
curl -fsS https://write.example.org/api/health
```

Проверьте обычный вход, владельца, книгу с другого устройства и один старый заказ. Если нужен прежний том, верните значение `KARETKA_DATA_VOLUME` из сохранённой конфигурации и повторите `docker compose up -d --wait`. Сверьте деньги с выпиской ЮKassa, особенно если восстановление выполнено из старой копии. Для тренировочного восстановления используйте новую изолированную установку с `BILLING_MODE=off`. Запуск второго публичного экземпляра с теми же платёжными ключами может принять рабочие уведомления дважды.

## 7. Обновление и откат

Перед выпуском сделайте резервную копию из раздела 5. Сохраните текущий commit, чтобы быстро вернуться к знакомому коду. В обычном цикле деплоя том данных подключается повторно.

```sh
cd /opt/karetka
git status --short
git rev-parse HEAD > /var/backups/karetka/previous.commit
git switch main
git pull --ff-only origin main
release=$(git rev-parse --short=12 HEAD)
sed -i "s/^KARETKA_RELEASE=.*/KARETKA_RELEASE=$release/" .env
docker compose config --quiet
docker compose build --pull app
docker compose up -d --wait
docker compose ps
curl -fsS https://write.example.org/api/health
```

Проверьте сайт в приватном окне и в уже открывавшемся редакторе. На устройстве с прежней офлайн-версией может потребоваться повторно открыть вкладку при включённой сети. Входящие webhook должны по-прежнему приходить на тот же адрес.

При неполадке остановите выкладку и посмотрите `docker compose logs --tail=150 app web`. Если формат базы совместим с предыдущей версией, верните прежний код и ранее собранный образ.

```sh
cd /opt/karetka
previous=$(cat /var/backups/karetka/previous.commit)
git switch --detach "$previous"
release=$(git rev-parse --short=12 HEAD)
sed -i "s/^KARETKA_RELEASE=.*/KARETKA_RELEASE=$release/" .env
docker compose up -d --no-build --wait
```

Если образ уже удалён, соберите его в каталоге прежнего коммита. Изменения схемы проверяйте по описанию конкретного релиза. Откат приложения и возврат базы к старой дате — разные операции. Перед возвратом базы учтите рукописи и покупки, появившиеся после копии. Для обычной остановки используйте `docker compose stop`. Ключ `down -v` предназначен для удаления именованных томов.

## 8. Как перенести старые рукописи и проверить новый домен

- На исходном устройстве откройте прежний адрес, дождитесь статуса сохранения в сети. Для гостевых и локальных рукописей сохраните **Экспорт → JSON** по каждой нужной книге. JSON включает структуру, карточки и планы. Он содержит читаемый текст, поэтому выбирайте личное место хранения.
- На новом устройстве и домене войдите в нужный аккаунт. Откройте **Рукописи → Открыть из файла** и проверьте главы, сцены и карточки. После синхронизации проверьте результат с другого устройства. Держите старый адрес и исходные выгрузки доступными до окончания проверки.
- Прежняя пара устройств с гостевым кодом продолжает работать с уже созданным хранилищем на том же сервере. Новые облачные библиотеки создаются в аккаунтах. На чистом VPS собственные SQLite и учётные записи. Гостевой код с Netlify сам по себе не переносит туда содержимое.
- Экспорт одной книги переносит её текст и структуру. Учётные записи, заказы и права хранятся отдельно. При запуске нового проекта самый простой момент для переезда на VPS — **до открытия реальных продаж**. Для переезда работающего магазина проведите перенос серверных записей и сверку с реестром платежей до отключения прежнего сайта.
- При появлении второго публичного адреса храните один основной адрес для оплат, вебхуков и входа. На обоих хостингах служебные секреты, резервные копии и папки данных находятся вне каталога `dist`.

## Быстрая диагностика

| Симптом | Что проверить |
| --- | --- |
| DNS ведёт на чужой сервер или TLS не выдаётся | Ответы `A`/`AAAA` извне, доступность TCP 80/443, `docker compose logs web`, ограничения CAA у регистратора |
| Caddy показывает HTTP 502 | `docker compose ps`, `docker compose logs app`, готовность `/api/health` и права записи на том |
| Кабинет доступен, оплата закрыта | Режим, ключ нужного магазина, реквизиты продавца, HTTPS-ссылки, схема чеков и пересоздание контейнера после правки `.env` |
| Оплата прошла, заказ в ожидании | Правильный webhook, события в кабинете ЮKassa, открытие заказа в «Каретке» для повторной проверки |
| Вход на новом домене открыл пустую библиотеку | Адрес и устройство, выбранный аккаунт, доступна ли его исходная БД, статус синхронизации на прежнем адресе |
